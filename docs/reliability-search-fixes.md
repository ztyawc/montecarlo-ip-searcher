库内 `engine.New` 现在保留调用方的原始配置，使用者应从 `engine.DefaultConfig()` 开始再覆盖所需字段。`--download-top=0` 仍表示关闭下载；`--download-bytes=0` 在自定义 URL 下表示不设字节上限，在默认端点下使用 50 MB。`--skip-first` 必须小于 `--rounds`。

输出文件替换保留已有文件的权限，新文件默认 `0600`。为避免替换符号链接或设备本身，`--out-file` 只接受普通文件路径；管道可使用标准输出。写入成功包括文件刷新，但没有额外同步父目录，也未做 Windows 实机验证，不能将其理解为突然断电时的持久性保证。

树容量包含父节点与子节点，默认 65,536。若初始输入网段已经更多，则保留这些输入并停止进一步扩展，避免悄悄丢失覆盖范围。固定种子可在固定输入及反馈顺序下复现采样；实际网络延迟和并发返回顺序仍影响后续选择。

连接释放按候选 IP 的生命周期管理。HTTP/2 取消后仍可能异步清理请求流，仅调用 `CloseIdleConnections` 会漏掉此时尚未空闲的连接；现在登记本 IP 拨出的连接，整组结束时明确关闭。若自定义拨号器在取消后才返回连接，该连接也会立即关闭。

离线算法对照使用保留测试地址 `198.18.0.0/20` 中的 4,096 个地址，每种方法、每个种子都采样 512 个不同地址，共 24 个种子。MCIS 使用实际选网段、IP 去重、反馈更新及细分代码，4 个搜索头、Beam 32、超时代价基准 1 秒，其余采用默认搜索设置；合成反馈同步返回，不启动探测线程或网络连接。均匀随机在全体地址中无放回采样，分层采样为每个 `/24` 均匀分配预算。

每个 IP 的成功/失败和延迟在该合成世界中固定，不模拟同一 IP 随时间随机失效。下表是最终成功结果前 10 名的平均延迟，取 24 个种子的均值，单位毫秒，越低越好：

| 合成场景 | MCIS | 均匀随机 | 分层采样 |
| --- | ---: | ---: | ---: |
| 优质 IP 集中在少数网段 | 15.00 | 16.55 | 16.71 |
| 优质 IP 分散分布 | 19.53 | 18.98 | 19.46 |
| 低延迟网段包含大量失败 IP | 21.64 | 19.51 | 18.79 |
| 延迟差异很小 | 100.00 | 100.00 | 100.00 |

高失败场景下，三种方法采样到的失败比例分别为 17.15%、12.50%、12.14%；MCIS 的前 10 名平均值在不同种子间的标准差约 9.36 毫秒，另外两种约 1.98 和 0.87 毫秒。该结果体现当前策略在这个场景中的局限，不能宣称固定预算一定找到全局最优，或普遍优于随机采样。它也不能证明真实网络中的提速幅度。

候选选择的组件微基准在本机 Linux/amd64、Intel Core i7-9750H 上执行，每组运行 250 毫秒，重复三次取中位数。下表为单次选择耗时，单位微秒：

| 活跃叶节点数 | Beam 1 | Beam 32 | Beam 256 |
| --- | ---: | ---: | ---: |
| 256 | 0.269 | 3.059 | 22.128 |
| 4,096 | 0.274 | 3.059 | 22.936 |
| 65,536 | 0.328 | 3.206 | 23.399 |

固定 Beam 后，选择耗时不再随全部叶节点数大幅增长。Beam 32 的三种规模均报告 `0 B/op`、`0 allocs/op`。树达到 65,536 节点容量时，拆分候选检查直接返回；未积累观测与已有足够观测的中位数分别为 16.70 和 16.87 纳秒，均为 `0 B/op`、`0 allocs/op`。这些数据只说明选择和满树检查的组件开销，不能推导整次扫描或手机端的提速比例。
